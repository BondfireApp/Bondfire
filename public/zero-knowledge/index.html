ZERO-KNOWLEDGE // PLAIN LANGUAGE

The server should not need to read your private work.

Your private organization data is encrypted before Bondfire stores it. Authorized members decrypt the information they are permitted to access.

Publishing crosses a deliberate boundary. Public content is not represented as private encrypted workspace data.

IMPLEMENTATION

The current private-record implementation uses the browser’s Web Crypto API with AES-GCM authenticated encryption. Encrypted records are bound to organization/content identity through authenticated data, and scoped key access is role/device gated.

WHAT ZERO-KNOWLEDGE DOES NOT MEAN

  • It does not mean the hosted service knows literally nothing about accounts, requests, memberships, timestamps, or operational metadata.
  • It does not protect an already compromised endpoint.
  • It does not stop an authorized member from copying or screenshotting plaintext they can legitimately view.
  • It does not make recovery material harmless.
  • It does not protect information that a user intentionally publishes.

See What Bondfire Knows for the metadata/account boundary and Threat Model for practical limitations.

HOSTED + SELF-HOSTED

The same core Bondfire software supports hosted and self-hosted deployments. The hosted project can describe its own infrastructure and maintenance practices. A self-hosted operator controls their own infrastructure and is responsible for its configuration, logging, updates, backups, and security.
